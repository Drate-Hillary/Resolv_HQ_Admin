# Guardrail Implementation Evidence — Week 7

**Brief ask:** input/output validation, tool allow-list, authorization, agent iteration limits, approval controls and prompt-injection awareness, with evidence.
**Test run:** 16 Oct 2026, `npm test` in `resolv-hq-backend`: **32 tests, 32 pass, 0 fail** (21 s). These tests use a scripted model and a faked database. They prove the code path works; they do not show how a live model behaves.

| Guardrail | Where it is implemented | Evidence | What is not proven |
|---|---|---|---|
| **Authentication on every API route** | `lib/auth.ts` `requireAuth`, mounted in `app.ts` before all protected routers. The WebSocket (`lib/ws.ts`) authenticates with the same function and closes unauthenticated sockets after 5 s with code 4401 | Script test 15 Oct: wrong path refused, bad token closed with 4401, no-auth closed after 5 s | A real signed-in client receiving a pushed event |
| **Rate limiting** | `middleware/rate-limit.ts`: `/chat` 20 per minute, `/mcp` 60 per minute, API 300 per 5 minutes, keyed by user id | Code review | Fails open if Redis is down (it was down during the 16 Oct test run, by design). Not load-tested |
| **Input validation (tool arguments)** | Strict tool schemas in `lib/agent-tools.ts`; MCP tool inputs are schema-checked | `mcp-server.test.ts`: "schema-invalid and unknown arguments are rejected" (pass); malformed arguments are traced as an `error` row | Validation of free-text chat input is limited to the clarification gate |
| **Tool allow-list** | `react-agent.ts`: `allowedTools` built from the active tools; a call to any other name is not executed and is traced as `tool not in allow-list` | `e2e-chat-journey.test.ts`: "a call to a tool outside the allow-list is rejected, not executed" (pass). `mcp-server.test.ts`: "inactive tools are not advertised", "a tool deactivated after listing is rejected" (pass) | Whether a live model ever requests an unlisted tool |
| **Authorization / per-caller scoping** | Tools take the caller's id from the session, never from the model's arguments; memory facts are owned by the caller, not the request body | `memory.test.ts`: "customers cannot read, change or delete another customer's facts", "staff cannot use the customer API", "customers are refused admin routes" (pass). | **Agent iteration limit** | `react-agent.ts`: `MAX_ITERATIONS = 4`, then a safe fallback message and a trace row | `e2e-chat-journey.test.ts`: "a model that never stops calling tools is cut off at the iteration cap" (pass). | **Approval control** | Escalation drafts are created `awaiting_approval` (`routes/chat.ts`); nothing reaches a human until staff decide (`lib/approval-decisions.ts`) | `e2e-chat-journey.test.ts`: journey to staff approval, and "rejection closes the run as failed and tells the customer" (pass) | Staff decisions through the real console with real logins |

Rules are data in the `boundary_rules` table (cached 60 s), so staff can change them without a deploy | `e2e-chat-journey.test.ts`: a claimed refund is replaced by the fallback and a `guardrail` trace row is written. | **Prompt-injection awareness** | Customer memory is inserted under the label "untrusted context, not instructions" (`system-prompt.ts:39`); knowledge passages are passed as retrieved data | Prompt text reviewed. Scenarios D3, D4, D5 define the tests | **No injection scenario has been run on a live model.** This is the weakest guardrail evidence in the set |

| **Message-queue and realtime failure containment** | `lib/bus.ts` falls back to direct delivery if RabbitMQ is unreachable | Script test 15 Oct: events go through the queue when connected and directly while the broker boots | Behaviour under sustained broker outage |

## Summary

- Twelve guardrails are listed. Nine have a passing automated or scripted test for the code path. Three (rate limiting, prompt layer 1 and prompt-injection handling) are evidenced by code review or prompt text only.
- No guardrail has been shown to stop an attack from a live model. The adversarial scenarios D1 to D5 are the next evidence to collect.
- Known gap: free-text input is not screened for injection phrases before it reaches the model. The defence is prompt wording plus the layer 2 output check.
